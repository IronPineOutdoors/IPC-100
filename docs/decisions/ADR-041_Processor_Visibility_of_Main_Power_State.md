# ADR-041 — Processor Visibility of Main Power State

> **ADR-044 amendment:** GPIO42 is now `WATCHDOG_SERVICE_MCU`; GPIO37 remains reserved. The decision that `MAIN_POWER_GOOD` is not firmware-visible remains unchanged.

## Context

ADR-039 establishes `MAIN_POWER_GOOD` as the active-high, fail-low result of qualified protected main input and an in-tolerance `+5V_MAIN` regulator. Sheet 02 owns its generation and uses it to hardware-qualify every request-controlled peripheral branch. Sheet 06 consumes it independently as one input to fail-low actuator authorization.

ADR-040 allocates or reserves all 36 GPIOs exposed by ESP32-S3-WROOM-1-N8. It did not allocate a GPIO for `MAIN_POWER_GOOD`, but retained Sheet 03 as a consumer. Package 04R correctly stopped rather than duplicate an assignment, consume GPIO37/42 without approval, gate EN, or leave an unexplained port.

## Problem statement

The architecture must decide whether firmware needs direct visibility of qualified main power. A signal shall not remain at the processor boundary merely because an earlier hierarchy draft exposed it.

The decision must preserve:

- hardware-enforced branch qualification on Sheet 02;
- hardware-enforced actuator authorization on Sheet 06;
- full USB-only programming, bootloader, recovery, debug, and diagnostics;
- ADR-040 GPIO assignments and reserves;
- distinct main-good, core-good, reset-valid, and fault-diagnostic semantics; and
- one electrical and functional owner for every cross-sheet signal.

## Responsibility review

| Sheet | Power ownership and supervision | Safety responsibility | Firmware responsibility | Hardware responsibility |
| --- | --- | --- | --- | --- |
| 01 | Protects the raw input and produces `MAIN_INPUT_VALID` and `POWER_FAULT_SUMMARY` | Forces protected-source fault behavior | None | Input protection, source validity, fault diagnostic |
| 02 | Owns regulated rails, source mux, `MAIN_POWER_GOOD`, and switched branches | Prevents main-only branch energization without qualified main power | None | Qualifies main power; pulls requests low; gates every request; controls branches |
| 03 | Owns core supervision, reset, processor, and request generation | Keeps requests low through reset/boot; does not authorize actuators | Requests non-actuator peripherals after initialization | TPS3890 core supervision, reset validity, boot/recovery defaults |
| 06 | Consumes `MAIN_POWER_GOOD`, `RESET_VALID`, STOP health, and watchdog validity | Sole owner of actuator permit and fail-low response | May issue commands, but cannot bypass permit | Independently removes actuator authorization on invalid main power |

Detection belongs to the power and supervisor layers. Response that must occur without firmware remains on Sheets 02 and 06. Firmware owns operational intent, not power qualification.

## Options considered

### A — Hardware-only status owned by Sheet 02 and consumed where hardware needs it

`MAIN_POWER_GOOD` remains generated by Sheet 02, gates peripheral branches there, and feeds Sheet 06 actuator authorization. It is removed from Sheet 03.

Advantages:

- no GPIO consumption;
- fastest and deterministic fail-low response;
- no firmware dependency in either safety path;
- preserves USB-only service;
- keeps source qualification in the power layer;
- avoids duplicate policy and stale sampled state.

Disadvantages:

- firmware cannot directly display or log the qualified-main Boolean;
- operational source-state reporting must use behavior already observable to firmware or a future approved diagnostic channel.

### B — Firmware-visible GPIO

Advantages:

- direct source-state logging and user messaging;
- convenient software branch-policy input.

Disadvantages:

- consumes or displaces a frozen GPIO;
- provides no additional enforcement because Sheets 02 and 06 already act in hardware;
- creates sampling, debounce, and stale-state semantics;
- risks software treating observation as authorization.

Rejected.

### C — Reset-supervision input

This would gate ESP32 EN or core reset with `MAIN_POWER_GOOD`.

Advantages:

- processor runs only with qualified main power.

Disadvantages:

- disables required USB-only programming, bootloader, recovery, debug, and diagnostics;
- conflates main validity with core validity;
- defeats the purpose of the main/USB core-source mux.

Rejected.

### D — Diagnostic-only processor signal

Advantages:

- retains direct observability without granting safety authority.

Disadvantages:

- still consumes a GPIO;
- no released diagnostic requirement justifies displacing baseline or reserved resources;
- `POWER_FAULT_SUMMARY`, rail measurements, and future diagnostic expansion have distinct semantics and must not be aliased.

Rejected for Rev A. A later revision may add a controlled diagnostic channel.

### E — Internal-only Sheet 02 signal

Keeping `MAIN_POWER_GOOD` entirely internal to Sheet 02 would simplify routing, but Sheet 06 requires it for hardware actuator authorization.

Rejected. The signal remains a cross-sheet hardware status from Sheet 02 to Sheet 06.

## Safety analysis

Firmware visibility does not improve the two safety-relevant responses:

1. Sheet 02 gates all four peripheral requests with `MAIN_POWER_GOOD`. Firmware cannot energize a branch when main power is invalid, even if a request is stuck high.
2. Sheet 06 includes `MAIN_POWER_GOOD` in `ACTUATOR_PERMIT`. Invalid main power removes actuator authorization without processor execution.

Removing the Sheet 03 consumer therefore removes no enforcement, detection, or fail-low response. It reduces the chance that software code or documentation mistakes an observed status for authority.

## USB-only analysis

USB-only mode shall continue to support:

- native-USB programming;
- UART recovery;
- ROM bootloader entry;
- reset and BOOT controls;
- debug;
- bounded core diagnostics.

`MAIN_POWER_GOOD` is false during USB-only operation by design. It shall not gate `+3V3_CORE`, ESP32 EN, TPS3890 supervision, USB PHY operation, UART recovery, or boot straps. Removing it from Sheet 03 preserves this behavior with no special firmware case.

## Firmware analysis

Rev A firmware does not require the qualified-main Boolean to make a safe decision:

- peripheral branch availability is enforced by Sheet 02;
- actuator availability is enforced by Sheet 06;
- firmware may request peripheral power but does not decide whether main power is electrically valid;
- a request that cannot be honored is safe and shall be handled as an unavailable peripheral;
- the processor remains operational during USB-only service without claiming product readiness;
- battery measurement may support user information when meaningful, but is not a substitute for `MAIN_POWER_GOOD`;
- source transitions are owned by the Sheet 02 mux and hardware state machines;
- exact branch feedback is not provided, so `MAIN_POWER_GOOD` alone would not prove a branch is energized.

Firmware shall never infer actuator authorization from USB presence, battery voltage, request state, or peripheral response.

## Selected architecture

Select Option A.

- Sheet 02 remains the sole producer and electrical owner of `MAIN_POWER_GOOD`.
- Sheet 02 remains the consumer for its own branch-gating logic.
- Sheet 06 remains the only cross-sheet functional consumer.
- Sheet 03 is removed as a consumer.
- Firmware does not directly observe `MAIN_POWER_GOOD` in Rev A.
- Sheet 03 continues to create local `CORE_POWER_GOOD` and export `RESET_VALID`.
- `MAIN_INPUT_VALID` remains Sheet 01-to-02 only.
- `POWER_FAULT_SUMMARY` remains a distinct input-path diagnostic and is not routed to Sheet 03.
- ADR-040 GPIO assignments, GPIO37/42 reserve, and the allocation validator remain unchanged.

Firmware requests peripheral power as operational intent. Sheet 02 decides electrically whether each request can be honored.

## Consequences

- The Package 04R GPIO conflict is eliminated without reassignment.
- GPIO37 and GPIO42 remain reserved.
- USB-only service remains independent of main qualification.
- Sheet 03 has no main-power status input.
- Sheet 06 retains deterministic hardware power-fault response.
- Firmware cannot directly report `MAIN_POWER_GOOD`; future direct reporting requires an approved diagnostic path or later revision.
- Sheet 00 and Sheet 03 hierarchy ports shall remove `MAIN_POWER_GOOD` during Package 04R interface synchronization. Sheet 02-to-06 routing remains.

## Migration impact

The following controlled text is amended:

- ADR-039 consumer tables: replace “Sheets 03 and 06” with “Sheet 06” for `MAIN_POWER_GOOD`.
- ADR-040 status table and Package 04R description: remove Sheet 03 consumption.
- GPIO review: state that no GPIO is required for main-good visibility.
- hierarchy definition: remove Sheet 03 as a consumer while preserving Sheet 02-to-06.
- Package 04R entry-gate record: close the blocker and authorize implementation.

No component, GPIO, rail, Sheet 02 circuit, or Sheet 06 logic changes are authorized by AR-03.

## Verification requirements

- Confirm the authoritative GPIO inventory remains 36 unique rows with no reassignment.
- Confirm GPIO37 and GPIO42 remain reserved.
- Confirm Sheet 02 still gates every request with `MAIN_POWER_GOOD`.
- Confirm Sheet 06 still consumes `MAIN_POWER_GOOD` in fail-low actuator authorization.
- Confirm Package 04R removes only the Sheet 03 hierarchy port and does not remove the Sheet 02-to-06 net.
- Confirm ESP32 EN and reset depend on core supervision, not main qualification.
- Exercise USB-only programming, bootloader, UART recovery, debug, and diagnostics.
- Exercise main loss while USB retains the core and verify all main-only branches and actuator permit become inactive in hardware.
- Verify firmware documentation does not claim main-power qualification visibility.

## Rejected alternatives

- consume GPIO37 or GPIO42;
- duplicate an assigned GPIO;
- displace a baseline application or recovery signal;
- gate ESP32 EN/reset with main qualification;
- alias `MAIN_POWER_GOOD` to battery sense, `CORE_POWER_GOOD`, `RESET_VALID`, or `POWER_FAULT_SUMMARY`;
- add an expander, latch, ADC mux, or inferred software substitute solely for main-good visibility;
- make `MAIN_POWER_GOOD` internal to Sheet 02 and remove Sheet 06 hardware visibility.
